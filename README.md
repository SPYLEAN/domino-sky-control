# DOMINO SKY: CONTROL

**Predict the ripple. Break the chain.** — *Engineered for truth. Designed for clarity.*

Live: https://domino-sky-neon.vercel.app · Repo: https://github.com/SPYLEAN/domino-sky-control

Domino Sky is an interactive airline-disruption simulator. Close any of the 16 airports in the organisers' dataset for any window, and a **deterministic engine** computes how the closure spreads through aircraft rotations, passenger connections and crew duty limits. A **recovery optimizer** then searches real, feasible dispatcher actions, simulates each one in full, and proves why the recommended plan wins. Every number on screen comes from code — never from an AI model.

> This is a what-if model of a single-day dataset. It is not a live flight network and does not use any external flight data.

## 2. Product tour

1. **The Domino Effect** — a 20-second intro whose six lines are filled from the live Mumbai simulation.
2. **Create the storm** — pick airport, closing time and duration → *Simulate Disruption*.
3. **Watch the dominoes** — SVG network map (real lat/lng), rotation timeline (one row per aircraft, scheduled ghost vs. simulated bar, closure band), play / pause / scrub / speed.
4. **Understand why** — click any flight → *Flight DNA* with the **Reasoning Lens**: *What happened?* (plain English) · *Why did it happen?* (causal chain of ledger events back to the root) · *Show the proof* (formulas, timestamps, raw event records).
5. **Recover** — ranked, fully-simulated plans with feasibility checks, the **Recovery Decision Journal**, and a dispatcher explanation (Gemini if configured, otherwise clearly labelled *rules-based*).
6. **See the difference** — apply a plan; KPIs animate to new computed values, routes turn mint where things improved, and a before/after table lists exactly what changed.
7. **The Domino Story** — a 7-scene fullscreen replay (Normal operations → Crisis → First domino → Cascade → Human impact → Dispatcher → Resolution) generated by `buildStory()` from the event ledger. Play / Pause / Next event / Previous event / Replay / Exit, keyboard controls, subtitles, reduced-motion support. Scenes say plainly when a scenario produced nothing of that kind.
8. **Event Ledger** — searchable, filterable list of every engine event; click to sync map, timeline, flight and causal trace back to the earliest recorded cause. Toggle between operational time and engine calculation order.
9. **Guide me** and **What am I looking at?** — contextual, non-technical explanations.

## 4. Dataset

`src/data/flight_network.json` (copied verbatim, never mutated; a test asserts this). Parsed and validated with Zod plus referential-integrity checks in `src/engine/data.ts`.

Verified invariants (tests): 16 airports · 70 flights · 16 operating aircraft · 21 connection groups · 16 crews · 2 spares (VT-DS17 @ BLR, VT-DS18 @ DEL, from 05:00) · 10,394 scheduled boardings · 659 connection bookings · baseline turnarounds ≥ 30 min, all connections made, all crews legal.

## 5. Simulation model

**Time.** Integer minutes from 00:00 IST of the operating day; scheduled and actual times stored separately; values past 24:00 render as `HH:MM +1d`. The user's system timezone is never used.

**Processing order.** All flights sorted by scheduled departure (tie: flight id). Every aircraft and crew sequence is ordered by scheduled time, so this is a valid topological order of all dependencies.

**Earliest departure** for an operable flight:
```
aircraft_ready = arrival of the aircraft's previous operated leg + 30   (spare: available_from)
crew_ready     = arrival of the crew's previous operated leg + 30       (first leg: duty_start)
earliest       = max(scheduled_dep, aircraft_ready, crew_ready, dispatcher_hold)
```
The **binding constraint** is the single term that sets `earliest` (ties resolve to schedule → aircraft → crew; a dispatcher hold is binding only when strictly later). Overlapping causes are never added together.

**Airport closure policy** (closed interval is `[start, end)`):
1. If the departure falls inside a closure at the origin → depart at reopening.
2. If the resulting arrival falls inside a closure at the destination → **planned ground hold** at origin: depart `end − block`, so it lands exactly at reopening.
No mid-air holding, diversions or ferry flights are simulated, because the dataset contains no fuel/diversion data.

**Aircraft continuity.** An aircraft can only fly a leg from the airport where it physically is. If a leg is cancelled, the aircraft stays put and any later leg that starts elsewhere is cancelled as *aircraft out of position* (with the cause flight recorded). The same rule applies to crews.

**Crew duty.** `duty = actual arrival − duty_start`. If a flight would push its crew over `max_duty_mins`, it is **not flown** (`crew_duty_limit`): there are no reserve crews in the data, so we never invent one. Aircraft and crew remain at the origin, and continuity rules then cancel their later legs.

**Connections.** Made iff both legs operate and `outbound actual dep ≥ inbound actual arr + min_connect_minutes`. Otherwise *missed* (timing) or *broken* (inbound / outbound cancelled). Groups whose slack shrank below 15 min are flagged *at risk*.

**Capacity.** Combined arrivals + departures per airport per clock hour (`floor(t/60)`) are **monitored** against `capacity_per_hour` and reported; they are not enforced (no scenario in this dataset comes close).

**Invariant checker.** `checkInvariants()` independently re-verifies every result: no departure before schedule, block time unchanged, nothing inside a closure, no teleporting aircraft/crew, turnaround ≥ 30, crew duty legal, spares used only after `available_from` from their base.

**Determinism.** No randomness, no clocks, stable sort tie-breakers; identical inputs produce byte-identical JSON (tested).

### Event ledger
Each result contains `events[]` with `id`, `seq` (engine calculation order), `type`, `time` (simulated operational time), affected airport / flight / aircraft / crew / connection, `prevState`, `newState`, `parentId` (cause), machine-readable `rule`, human `explanation`, and computed `values`. Types: `closure_start`, `closure_end`, `closure_constraint`, `flight_rescheduled`, `rotation_propagation`, `crew_infeasible`, `flight_cancelled`, `connection_missed`, `connection_at_risk`, `recovery_assignment`. Recovery evaluations are recorded in the **Decision Journal**.

## 6. Passenger metrics — and their limits

Reported separately, never silently summed:
1. **Cancelled boardings** — pax on cancelled flights.
2. **Missed-connection passengers** — sum of group sizes for groups not made.
3. **Passengers on delayed flights** and **passenger-delay minutes** (pax × delay).
4. **Modelled stranded-passenger cases (proxy)** = cancelled boardings + passengers in groups missed *on timing* (both legs flew). Groups broken by a cancellation are already inside the cancelled boardings and are not added again. Because the dataset has boardings, not passenger identities, one traveller booked on two cancelled flights is counted twice — this is a reproducible operational proxy, **not** a count of unique people (tooltip in the UI says so).

## 7. Recovery optimizer

**Actions (only real dataset resources):**
- **Hold for connection** — keep a connection's onward flight on the ground until `inbound actual arr + min_connect` (≤ 180 min).
- **Cancel round trip** — cancel legs *k, k+1* when *k+1* returns to *k*'s origin, so the aircraft absorbs delay in place.
- **Cancel rest of rotation** from leg *k*.
- **Spare aircraft** — VT-DS17/VT-DS18 fly a consecutive block of legs (rest-of-day takeover or a round trip that returns to base) **only** if the first leg departs from the spare's physical base. The operating crew must be a dataset crew who is physically at that airport and scheduled to be free — either the scheduled crew or a crew whose own day ends there. A spare is never moved without flying a scheduled leg and is never double-committed.

**Search.** Scope = rotations of every aircraft with a delayed/cancelled flight or a broken connection. Every single action is pre-checked structurally, then **fully re-simulated** and re-checked against all invariants; reassigned legs must actually operate (e.g. the new crew must stay within duty). A bounded beam then combines the top 8 single actions on different aircraft into two-action plans. Ranking is stable (score vector → fewer actions → id).

**Objectives** (selectable):
- *Protect passengers* (default, lexicographic): cancelled boardings → missed-connection pax → passenger-delay minutes → flight-delay minutes → interventions.
- *Reduce total delay*, *Minimise cancellations* (lexicographic variants).
- *Balanced*: 180 × cancelled boardings + 120 × missed-connection pax + passenger-delay minutes.

The result is labelled **"Best evaluated recovery under the displayed search scope"** — the search is not exhaustive, so global optimality is never claimed. *Preserve current schedule* is always a candidate and wins whenever nothing beats it.

Why spares rarely help in this dataset (and the UI says so): crews fly with their aircraft, so a late aircraft means a late crew. A spare only helps when a different, legal crew is physically at BLR/DEL — the journal shows how many spare/crew pairings were rejected and why.

## 8. AI responsibilities and safeguards

`POST /api/dispatcher` recomputes the scenario on the server, sends Gemini (`@google/genai`, structured JSON output with an enum of real candidate ids) only engine facts, and passes the reply through `sanitizeAiResponse()`:
- schema must match; selected id must be one of the engine's candidates;
- any flight / tail / crew / connection id must exist in the dataset;
- **any digit** left after removing verified ids → reject.
Rejected or failed responses fall back to the deterministic `rulesExplanation()`, labelled "Rules-based". Figures shown beside the explanation are rendered from the engine result, never from model text. API keys stay server-side.

## 9. Known limitations
- Single operating day; no overnight positioning or next-day recovery.
- Crew connection time is taken as the dataset's 30-min minimum turnaround (no separate crew rule exists in the data).
- Capacity is monitored, not enforced.
- Recovery search is bounded (single actions + top-8 pairwise beam), not exhaustive.
- No passenger re-accommodation onto other flights (no seat-level data beyond 180 seats/aircraft).
